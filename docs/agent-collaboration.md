# 智能体协作基础

本文定义本仓库的协作方式：分支模型、提交规范、PR 流程、证据要求，以及多个智能体并行工作时的边界。
目标是让「人类 + 多个智能体」在同一仓库上协作时，**改动可追溯、结论可验证、责任可界定**。

## 1. 基本原则

1. **小步、可回退**：一次 PR 只做一件事。宁可两个小 PR，不要一个混合大 PR。
2. **证据优先于叙述**：任何「已完成」「已验证」的表述都必须附带可复现的证据（命令 + 输出摘要）。见第 6 节。
3. **诚实标注未验证项**：做不到、没跑过、没条件验证的部分，在 PR 里显式写出来。隐瞒比失败更严重。
4. **人类是最终决策者**：涉及对外披露、知识产权、产品结论、招聘判断的决定只能由人类 Owner 做出。

## 2. 角色与事实来源

| 角色 | 主要责任 | 无权自行决定的事项 |
|---|---|---|
| 人类 Owner | 产品方向、优先级、权限授权、最终验收 | 无 |
| Codex | 需求拆解、技术方案、架构约束、代码审查、最终集成 | 不替代人类作产品与披露决定 |
| WorkBuddy | 边界明确的实现、测试、文档和问题修复 | 不自行扩大范围、改变架构或合并 PR |

- **GitHub Issue 是任务事实来源**：记录目标、主负责人、范围、验收标准、依赖和当前状态。
- **Pull Request 是实现与评审事实来源**：记录代码、测试证据、风险、审查意见和合并结果。
- **`AGENTS.md` 与 `docs/` 是稳定知识来源**：记录长期规则、产品边界和架构事实，不承担实时任务队列职责。
- 对话和本地临时文件可以辅助执行，但不能作为跨智能体唯一交接记录。

## 3. 分支模型

- `main` 是唯一长期分支，保持可运行。**不直接向 `main` 推送**，一律通过 PR。
- 每个智能体使用独立克隆或 Git worktree。即使任务相关，也禁止在同一工作目录或同一分支并发写入。
- 工作分支短生命周期，从最新 `main` 切出，合并后删除。
- 命名约定：`<类型>/<简短主题>`

| 类型 | 用途 | 示例 |
|---|---|---|
| `feature/` | 新功能 | `feature/plan-source-binding` |
| `fix/` | 缺陷修复 | `fix/sse-cross-process-loss` |
| `docs/` | 文档 | `docs/collaboration-foundation` |
| `chore/` | 构建、依赖、配置 | `chore/ci-unit-tests` |
| `refactor/` | 不改变行为的重构 | `refactor/evidence-validation` |

智能体分支使用单层工具前缀，避免归属不清：`codex/<类型>-<主题>`、`workbuddy/<类型>-<主题>`。例如 `workbuddy/feature-plan-source-binding`。一个 Issue 同一时刻只能有一个主写分支。

## 4. 提交规范

采用 Conventional Commits，描述用中文：

```
<type>(<scope>): <一句话说明做了什么>

<可选正文：为什么这么做、影响范围、取舍>
<可选脚注：Refs #12 / 未验证项说明>
```

- `type`：`feat` / `fix` / `docs` / `chore` / `refactor` / `test` / `perf` / `build`
- `scope`：包或目录名，如 `api`、`web`、`domain`、`contracts`、`database`、`llm`、`docs`、`ci`
- 提交信息描述**改动**，不要写「优化代码」这类无信息量的句子。
- 一次提交保持单一意图；不要在同一提交里混入格式化无关文件。

示例：

```
docs(collaboration): 新增智能体协作基础文档

补充分支模型、提交规范、PR 证据要求与多智能体并行边界。
未验证项：本文档未包含 CI 实际运行结果。
```

## 5. Issue 与 PR 流程

1. 先创建或认领一个 GitHub Issue，明确主负责人、目标、非目标、允许修改范围、验收标准和测试要求。
2. 从最新 `main` 创建独立工作副本与智能体专属分支，完成改动。
3. 本地跑最小验证集（见第 6 节），把命令与结果记下来。
4. 推送分支，按 `.github/PULL_REQUEST_TEMPLATE.md` 填写 PR，并关联 Issue。
5. Codex 负责技术审查与集成建议；涉及产品边界、对外披露或权限的决定交给人类 Owner。
6. **任何智能体都不得自行合并 PR。**合并必须经过人类 Owner 授权。
7. 合并方式：优先 Squash 或 Rebase，保持 `main` 线性可读。

PR 正文必须包含四个部分：

- **改了什么**：逐项列出文件与意图；
- **为什么**：关联的问题或动机；
- **验证情况**：跑了什么命令、结果如何、哪些没跑；
- **风险与回滚**：可能影响的范围，以及如何回退。

## 6. 证据要求（按改动类型）

| 改动类型 | 至少需要提供 |
|---|---|
| 领域逻辑（`packages/domain`） | `pnpm test:domain` 通过；新增/修改的用例名 |
| 契约与 Schema（`packages/contracts`） | `pnpm test:unit` 通过；非法输入被拒绝的用例 |
| API 行为（`apps/api`） | `pnpm test:unit` + 相关 `test/api` 用例（需 `_test` 库）结果 |
| 前端（`apps/web`） | `pnpm typecheck` 通过；界面变更的截图或说明 |
| 文档（`docs/`） | 链接可达、命令与 `package.json` 一致；引用的事实能指向源码位置 |
| CI / 构建 | 说明该步骤在**无密钥、无数据库**环境下可运行的理由 |
| 任何改动 | `pnpm typecheck` 通过 |

**未能执行的验证必须在 PR 中写明原因**，例如「未配置 `_test` PostgreSQL，未运行集成测试」。

## 7. 多智能体并行协作与自动化边界

同一仓库可能同时有多个智能体在工作，遵守以下约定可避免互相破坏：

1. **各用各的工作副本和分支**。独立分支不能代替独立工作目录；两项都必须满足。
2. **一个任务只有一个主写智能体**。其他智能体通过 Issue / PR 提供审查意见，不直接改写该分支。
3. **不要改写他人正在推进的分支，也不要 force push 已推送的共享分支**。需要接手时新建分支并在 PR 中说明来源与差异。
4. **动态状态放在 Issue / PR**。不要让多个智能体反复修改同一个 `STATE.md` 或 `TASKS.md` 充当共享队列；任务专属交接文件应按 Issue 编号隔离。
5. **CLI 调度默认单向**：未来如启用，应由 Codex 根据已批准的 Issue 启动一次 WorkBuddy 任务。WorkBuddy 不得反向启动 Codex，也不得把新 CLI 进程声称为当前桌面会话。
6. **自动调度必须另行评审**：在具备原子任务认领、独立 worktree、权限最小化、超时、最大重试、成本上限、日志和熔断前，不启用定时轮询、无人值守服务或自动派单。
7. **禁止用 Git Hook 启动智能体**。`post-checkout`、`post-merge` 等普通 Git 操作不得隐式消耗额度或修改仓库。
8. **不要修改 `.gitignore`、CI、锁文件去「绕开」问题**。这些文件影响所有协作者，改动需在 PR 中单独说明理由。
9. **不要在没有授权的情况下扩大披露范围**：不引入真实数据、真实凭据、内部域名/IP。
10. **冲突时以 `main` 为准**，在独立分支上重新基于最新 `main` 变基，而不是强行覆盖。

## 8. 评审要点

Reviewer 重点检查：

- 是否有**事实膨胀**：把「设计存在」写成「已完成」，或把工程测试结果说成产品效果。
- 是否触碰了 [architecture.md](architecture.md) 中的架构不变量（LLM 不写事实、Evidence 硬约束、失败降级）。
- 是否新增了必然失败的 CI 步骤或依赖外部密钥的检查。
- 是否把未验证项写清楚了。
- 是否引入了真实数据或凭据。
