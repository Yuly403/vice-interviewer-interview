# 产品效果评测设计

> 状态：**建议评测方案，尚未由本脱敏仓库执行。**

## 工程测试与产品评测的边界

现有测试验证 Schema、状态机、证据规则、Prompt 隔离、错误处理、限流、SSE 等代码行为。它们能回答“约束是否生效”，不能回答“AI 建议是否真的帮助面试官”或“招聘判断是否准确”。历史 26 项 LLM 自动化测试属于工程防护测试，不等同于真实面试效果准确率。

## 建议数据集

建立经授权、严格脱敏的 Golden Dataset。每个样本包含 JD、简历、计划、按时间排序的逐字稿，以及两名以上资深面试官独立标注的“当时应该提示什么、哪些内容应该保持沉默、可接受证据区间”。若无法取得合规授权，应使用合成访谈，不复用真实候选人材料。

## 历史逐字稿时点回放

不能把完整逐字稿一次性喂给会中模型。应按真实时间顺序逐行回放，在每个历史时点只允许模型看到当时已发生的内容，并记录提示出现时间、重复次数、引用证据和后续面试官是否已经问到。这样才能避免未来信息泄漏。

## 推荐指标

| 指标 | 建议定义 | 主要风险 |
|---|---|---|
| Suggestion Precision | 专家认为“当时有帮助且可执行”的建议数 / 全部建议数 | 噪声过高会打断面试 |
| Coverage | Golden 应提示点中被系统覆盖的比例 | 漏掉关键核实点 |
| Redundancy | 与近期建议或已问问题实质重复的比例 | 反复追问、浪费时间 |
| Evidence Accuracy | quote、lineId、角色和语义归因全部正确的比例 | 错引、移花接木 |
| Latency | 从关键 TranscriptLine 入库到建议可见的 p50 / p95 | 提示到得太晚 |
| Silence Quality | Golden 标注为“不应提示”的窗口中保持沉默的比例 | 为了覆盖率过度发言 |
| Edit Rate | 面试官对 AI 草稿进行实质修改或删除的比例，并按修改类型拆分 | 草稿看似被使用但人工修正成本过高 |

## 评测流程建议

1. 固定 Prompt、模型版本、阈值和代码提交号；
2. 划分调参与盲测集合，避免在同一数据上反复优化；
3. 双人独立标注并处理分歧，记录一致性；
4. 同时报告总体和岗位/轮次分层结果；
5. 保存每次输出的输入时点、耗时、证据映射和失败类型；
6. 发布 Precision、Coverage、Evidence Accuracy、Latency 等原始结果，不用一个模糊“准确率”替代；
7. 通过离线门槛后再做小范围 shadow mode，不直接影响招聘决定。

## 建议准入门槛

具体数值需由业务共同确定。优先顺序应为 Evidence Accuracy 和安全性门槛，其次是 Suggestion Precision、延迟和覆盖度。任何阈值在真实执行前都只能写成目标，不能写成已达成结果。
